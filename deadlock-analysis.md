# Аналіз дедлоку (Частина 2)

## Код, що аналізується

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	var wg sync.WaitGroup
	ch := make(chan int) // небуферизований канал

	wg.Add(1)
	go func() {
		// симуляція важкої роботи
		ch <- 42
		wg.Done()
	}()

	wg.Wait()
	fmt.Println(<-ch)
}
```

## Мій промпт до ШІ

Мій промпт має явно вимагати від ШІ:

- **не просто переписати код**, а пояснити точну послідовність
  переплетення (interleaving) горутин, що веде до зависання;
- проаналізувати, чому виклик `wg.Wait()` перед читанням з
  небуферизованого каналу зупиняє виконання.

### Мій промпт

Проаналізуй наведений Go-код із `sync.WaitGroup` і небуферизованим каналом. Не починай із переписування чи виправлення коду. Спочатку покроково опиши можливе переплетення головної горутини та горутини-відправника: на яких операціях кожна з них зупиняється і чого саме очікує. Поясни, чому `wg.Wait()` перед читанням із `ch` створює циклічне очікування, згадай, що відправник викликає `wg.Done()` лише після завершення send, та поясни роль небуферизованого каналу. Наприкінці наведи мінімальні способи виправлення та поясни, чому кожен із них усуває блокування.

## Пояснення від ШІ

Нижче — покрокове пояснення переплетення горутин у відповідь на промпт.

### Відповідь ШІ

1. Головна горутина створює `ch` без буфера, збільшує лічильник `wg` до 1 і запускає відправника.
2. Відправник виконує `ch <- 42`. Оскільки небуферизований канал передає значення лише тоді, коли одночасно є отримувач, send зупиняється, доки інша горутина не прочитає з `ch`.
3. Головна горутина викликає `wg.Wait()` і також зупиняється: лічильник ще дорівнює 1, бо відправник не дійшов до `wg.Done()`.
4. `wg.Done()` стоїть після send, а receive стоїть після `wg.Wait()`. Отже, відправник чекає на receive, головна горутина чекає на `Done`, і ніхто не може перейти до операції, яка розблокує іншого. Це взаємне очікування й утворює дедлок. Не має значення, яка горутина першою отримала процесор: до того самого циклу очікування код зрештою доходить.

Мінімальне виправлення — спочатку прочитати значення з каналу, а вже потім чекати на `wg` (або прибрати `WaitGroup`, якщо він більше не потрібен). Отримання завершує send, після чого відправник виконує `Done`; очікування вже не блокує передачу. Інший варіант — буферизувати канал місткістю щонайменше 1: тоді send може завершитися без одночасного receive, і `Wait` зможе повернутися.

## Мінімальне виправлення

Робочу, тестовану версію виправлення реалізовано в
[`deadlock/fixed.go`](./deadlock/fixed.go) (функція `Run`), а
автоматична перевірка — у `deadlock/fixed_test.go`. Коротко опишіть
своїми словами, яку зміну порядку операцій (чи структури каналу) ви
застосували і чому саме вона усуває циклічне очікування.

У `Run` відправник надсилає `42` через небуферизований канал, а виклик `Run` одразу отримує значення. Отримання розблоковує send, тож функція повертає `42` без `WaitGroup` і без циклічного очікування. Для одного значення синхронізація самим каналом достатня.
